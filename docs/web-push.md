# Web Push уведомления

## Цель

Уведомлять пользователей о новых объявлениях о пропавших и найденных
животных рядом с ними. Получатели выбираются по координатам и радиусу,
а не по заранее заданному району.

## Схема работы

1. Пользователь публикует объявление о пропавшем или найденном животном.
2. Frontend отправляет данные объявления на сервер FastAPI.
3. Сервер проверяет данные и сохраняет объявление в PostgreSQL.
4. Объявление проходит проверку ИИ. После одобрения оно публикуется,
   фиксируется время публикации `published_at`.
5. От координат объявления выбираются пользователи в нужном радиусе
   (этапы рассылки описаны ниже).
6. Для этих пользователей берутся активные PushSubscription.
7. Сервер отправляет Web Push через pywebpush с подписью VAPID.
8. Браузер получает push-событие в Service Worker.
9. Service Worker показывает уведомление.
10. По клику пользователь переходит к объявлению.

Публикация после одобрения ИИ  
↓  
FastAPI: выбор получателей по координатам и радиусу  
↓  
Получение активных PushSubscription  
↓  
pywebpush + VAPID  
↓  
Push-сервис браузера (FCM, Apple, Mozilla)  
↓  
Service Worker  
↓  
Уведомление, клик, страница объявления

## Необходимые технологии

- **FastAPI** — серверная часть, общая Python-кодовая база проекта.
  Принимает подписки, выбирает получателей, отправляет push.
- **JavaScript** — регистрация Service Worker, запрос разрешения,
  создание подписки.
- **Push API** — создание `PushSubscription`.
- **Notifications API** — показ уведомления.
- **Service Worker** — получает push-событие, даже когда страница закрыта.
- **VAPID** — подпись, по которой push-сервис идентифицирует сервер.
- **pywebpush** — Python-библиотека для отправки Web Push из FastAPI.
- **HTTPS** — обязателен в production (для `localhost` и `127.0.0.1`
  браузеры делают исключение).

## Какие данные подписки хранить в PostgreSQL

Браузер возвращает `PushSubscription` с полями `endpoint`, `expirationTime`
и `keys` (`p256dh`, `auth`).

Таблица `push_subscriptions`:

| Поле | Тип | Описание |
|---|---|---|
| id | bigserial, PK | |
| user_id | FK на users | владелец подписки |
| endpoint | text, UNIQUE | адрес push-сервиса браузера |
| p256dh | text | публичный ключ браузера |
| auth | text | секрет аутентификации |
| expiration_time | timestamptz, NULL | если браузер его вернул |
| user_agent | text | для отладки |
| is_active | boolean | выключается при ответах 404 и 410 |
| created_at, updated_at | timestamptz | |

Особенности:

- У одного пользователя может быть несколько подписок (браузеры, устройства).
- Подписка идентифицируется по `endpoint`, повторная отправка того же
  `endpoint` обновляет ключи (upsert).
- `endpoint`, `p256dh` и `auth` нельзя логировать и отдавать наружу.
- Если push-сервис отвечает 404 или 410, подписка помечается неактивной.
- VAPID-ключи хранятся не в базе, а в переменных окружения.

## Связь подписок с координатами

Сама подписка не знает, где находится пользователь. Координаты хранятся
отдельно:

`user_locations`: `user_id`, `location` (`geography(Point, 4326)`, PostGIS),
`updated_at`.

У объявления своя точка: `pets.location` (`geography(Point, 4326)`) и
`published_at`.

Получатели объявления находятся одним запросом:

```sql
SELECT ps.*
FROM user_locations ul
JOIN push_subscriptions ps ON ps.user_id = ul.user_id AND ps.is_active
WHERE ST_DWithin(ul.location, :pet_location, :radius_m);
```

Связь выглядит так: `pet.location` → `user_locations` в радиусе →
`user_id` → активные `push_subscriptions`.

Открытый вопрос: откуда берутся координаты пользователя (адрес, геолокация
браузера или выбранная точка на карте) и как часто они обновляются.

## Рассылка по радиусу

Время отсчитывается от публикации объявления после одобрения ИИ
(`published_at`):

| Этап | Когда | Радиус |
|---|---|---|
| 1 | сразу | 1 км |
| 2 | через 30 минут | 3 км |
| 3 | через 2 часа | 5 км |
| 4 | через 6 часов | 10 км |

На каждом следующем этапе уведомление получают только те пользователи,
которым оно ещё не отправлялось (кольцо между прошлым и новым радиусом).
Для этого нужна таблица отправленных уведомлений
`push_deliveries(pet_id, user_id, stage, sent_at)`.

## Ограничения

- Пользователь сам разрешает уведомления и может отозвать разрешение.
- Поддержка Web Push зависит от браузера и ОС.
- На iOS и в некоторых мобильных браузерах есть дополнительные условия
  (например, установка сайта на экран «Домой»).
- Фокус и «Не беспокоить» в ОС скрывают баннеры, хотя push доставлен.

## Текущий статус

Рабочий пример лежит в `experiments/web-push/` (FastAPI, pywebpush, VAPID,
Service Worker). Подписки там временно хранятся в локальном файле
`subscriptions.json`. Подробности запуска в README примера.

Реализовано:

- регистрация Service Worker и запрос разрешения;
- получение `PushSubscription` и передача на FastAPI;
- отправка тестового push из Python и показ уведомления;
- переход по клику на страницу;
- понятные статусы при отказе от разрешения.

## Что требует дальнейшей реализации

- перенос серверной части в `backend`, браузерной в `frontend`;
- таблицы `push_subscriptions`, `user_locations`, `push_deliveries`;
- выбор получателей по координатам и радиусу (PostGIS);
- планировщик поэтапной рассылки (1, 3, 5, 10 км);
- защита от повторных уведомлений;
- переход из уведомления к конкретному объявлению;
- обработка устаревших подписок (404 и 410).
