# Подключение уведомлений: Лизе и бэкендеру

Ветка основана на PR №10 и содержит merge `feature/react-start` от 25 ноября.
Используется существующая страница Лизы `/#/notifications` и её `LocationPicker`.
Пользователь не регистрируется. Разрешение запрашивается только кнопкой.

## Лизе: готовые функции

`frontend/src/api/notifications.ts` экспортирует:

- `getNotificationState()` — проверка браузерной подписки и её состояния в базе;
- `enableNotifications({latitude, longitude})` — разрешение → подписка → сохранение;
- `saveNotificationPoint({latitude, longitude})` — изменение сохранённой точки;
- `disableNotifications()` — отключение в базе и браузере;
- `pushSupported()` — доступность Web Push в безопасном контексте.

Они уже подключены к `NotificationsPage.tsx`. Ошибка сервера не включает успешный
статус. Выбор на карте сначала меняет локальную точку; сохранение — отдельной кнопкой.
Координаты не отслеживаются постоянно и не берутся без действия пользователя.

`VITE_API_URL` — адрес общего FastAPI, локально `http://127.0.0.1:8010`.
Публичный VAPID-ключ браузер получает через GET `/api/push/vapid-public-key`:

```json
{"publicKey":"<URL-safe Base64 public key>"}
```

Отдельно копировать ключ в React не нужно. Приватный ключ и `PUSH_TEST_TOKEN`
никогда не добавлять в `VITE_*`. Рабочий публичный ключ станет доступен после
настройки постоянной пары VAPID бэкендером на сервере; локальная пара — тестовая.

## Запросы и ответы

Все тела — JSON. Секретные endpoint и ключи реальных подписок не сохранять в Git.

POST `/api/push/subscriptions` (201, повторный endpoint обновляется):

```json
{
  "endpoint":"https://fcm.googleapis.com/<browser-generated-endpoint>",
  "expirationTime":null,
  "keys":{"p256dh":"<from PushSubscription>","auth":"<from PushSubscription>"},
  "latitude":55.75,
  "longitude":37.62
}
```

Ответ: `{"message":"Subscription saved"}`. Координаты — обе или ни одной.
Широта [-90, 90], долгота [-180, 180], конечные числа в градусах WGS84.
Старые подписки без точки сохраняются, но не получают географическую рассылку.
POST без координат не стирает ранее выбранную точку.

POST `/api/push/subscriptions/state`:

```json
{"endpoint":"<browser endpoint>"}
```

Ответ: `{"is_active":true,"latitude":55.75,"longitude":37.62}`.
Для отсутствующей записи: `false`, `null`, `null`.
Endpoint служит идентификатором анонимной подписки; он передаётся в теле, не в URL.

PATCH `/api/push/subscriptions/location`:

```json
{"endpoint":"<browser endpoint>","latitude":55.76,"longitude":37.63}
```

Ответ: `{"message":"Location saved"}`; 404, если активной подписки нет.

DELETE `/api/push/subscriptions` с `{"endpoint":"<browser endpoint>"}`:
`{"message":"Subscription disabled","disabled":true}`.
Повторная отписка безопасна (`disabled:false`). Повторный POST снова активирует подписку.

## Общий Service Worker и адрес объявления

В React используется единственный `frontend/public/sw.js`, область — корень
React-приложения. В актуальной ветке Лизы PWA-worker ещё отсутствует. Если появится
кэширование PWA, его обработчики нужно добавить в этот файл и согласовать в review;
регистрировать второй worker для той же области нельзя.
Старая проверочная страница backend со своим `/web-push/sw.js` остаётся диагностической.

React уже использует HashRouter с `/pets/:id`, поэтому адрес объявления:
`FRONTEND_URL/#/pets/123`. Worker открывает или фокусирует этот адрес.
`FRONTEND_URL` задаётся на сервере (например `https://frontend.example`).
Worker расположен на домене React, даже когда FastAPI находится на другом домене.

## Бэкендеру: схема и вызов после публикации

DDL находится в `backend/notifications/schema.py` и выполняется существующим
`database.startup()`. Изменения схемы предлагаются для согласования в PR:

- `push_subscriptions.latitude`, `longitude` — nullable DOUBLE PRECISION;
- `push_deliveries(pet_id, endpoint, stage, status, created_at)`;
- уникальный ключ `(pet_id, endpoint, stage)` предотвращает повторный запуск.

Схема `lost_pets` здесь не изменена. В доступной ветке общего backend ещё нет
координат объявления, `published_at` и события одобрения ИИ. После их подключения:

```python
from notifications.service import send_announcement

# Только после успешной записи одобренного опубликованного объявления.
report = await send_announcement(
    pet_id=pet_id, latitude=latitude, longitude=longitude,
    title="Пропал питомец рядом", body="Краткий текст объявления",
)
```

Долгая отправка не должна задерживать HTTP-ответ публикации: бэкендер выберет
существующий фоновой механизм общего проекта. Автоматический вызов пока не добавлен.
Для проверки имеется защищённый POST `/api/push/send-announcement` с теми же пятью
полями. Тестовый метод доверяет переданному id и координатам, сам не публикует животных.
Полную проверку «публикация через реальный API → push» блокирует отсутствующая
модель координат/публикации в общем backend. До этого проверяем ручной вызов.

## Радиус и защита от дублей

`geo.py`: расстояние по поверхности сферы (гаверсинусы), радиус Земли 6 371 000 м.
Порог — **1000 метров**, граница включена. Точность сферы достаточна для пробного
этапа, это не геодезический расчёт по эллипсоиду. Тесты: 999 м, 1000 м, 1001 м,
отсутствие координат, переход через 180° долготы.

Сначала загружаются только активные подписки. Без точки они исключаются.
Для небольшого учебного проекта расстояния считаются в Python. При росте базы
можно перенести поиск в PostGIS.

`send_to_recipients()` принимает уже выбранный список. До сетевого запроса создаёт
запись доставки через INSERT ON CONFLICT DO NOTHING. Два процесса не отправят одно
объявление одной подписке на одном этапе повторно. Этап пока всегда 1.
Сбой сети или процесса оставляет failed/pending, автоматического повтора нет:
при таймауте неизвестно, принял ли push-сервис сообщение. Это предотвращает дубли,
но допускает пропуск доставки. Это не гарантия exactly-once. Учёт получателей
между разными этапами и расширение радиуса остаются следующим этапом.

## Запуск и ручная отправка

В `backend/.env`: обычные переменные общего сервера, постоянная пара VAPID,
`VAPID_CLAIMS_SUB`, `FRONTEND_URL`, случайный `PUSH_TEST_TOKEN` только у проверяющего.
Публичный сервер без `PUSH_TEST_TOKEN` возвращает 404 для обоих методов рассылки.
Неверный `X-Push-Test-Token` возвращает 403. В браузер пользователя токен не передаётся.

```bash
cd backend
python -m pip install -r requirements.txt
uvicorn main:app --reload
```

React: `npm ci`, `npm run dev`; в `.env.local` задать `VITE_API_URL`.
HTTPS обязателен кроме localhost. На iOS Web Push требует установленное на экран
«Домой» web-приложение; системный режим фокуса может скрыть баннер.

```bash
curl -X POST "$API_URL/api/push/send-announcement" \
  -H 'Content-Type: application/json' \
  -H "X-Push-Test-Token: $PUSH_TEST_TOKEN" \
  -d '{"pet_id":123,"latitude":55.75,"longitude":37.62,"title":"Пропал питомец рядом","body":"Помогите найти кота"}'
```

Ожидаемый ответ: `{"selected":1,"sent":1,"skipped":0,"failed":0}`.
Повторный вызов с тем же id: `sent:0, skipped:1`.
Для ручного тестового push всем: POST `/api/push/send-test` с тем же заголовком.

В review требуется подтвердить у Лизы root-worker и найденный маршрут объявления,
у бэкендера — DDL и точку будущего вызова. Согласование не считается выполненным
до их ответа. Прямые сообщения от имени Кати не отправлялись.
